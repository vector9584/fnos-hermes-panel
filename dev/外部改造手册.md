
## 2.5 身份与提权（卡在 sudo 就看这节）

**结论：你不需要任何额外授权。** 2026-11-07 实测：

```bash
$ ssh nas-host 'sudo -n -l'
    (ALL) NOPASSWD: ALL          # vector 本来就免密 sudo 到任何用户

$ ssh nas-host 'sudo -n -u hermes-agent id'
    uid=892(hermes-agent) gid=901(AppUsers)    退出码=0   # 切得过去
```

`dev/hermes-dev.sh` 第 19-22 行已经替你处理了：

```bash
if [ "$(id -un)" = "hermes-agent" ]; then 直接跑
else sudo -n -u hermes-agent env HOME=$HERMES_HOME "$@"   # 统一提权 + 补环境
fi
```

所以你**直接调用脚本就行**，`probe` / `deploy` / `restart` / `preview` 都不用手动 sudo。

### 那条报错是什么意思

```
hermes-agent is not in the sudoers file
```

这条在说 **hermes-agent 没有 sudo 权限** —— 这是正常的、故意的（她不该能提权）。
触发条件是：**你已经在 hermes-agent 身份下，又调了一次 sudo**。

正确姿势是**只在最外层提权一次**，别在提权后的进程里再 sudo。用脚本就自动满足。

### 三条别做

1. **别自己写 `sudo -u hermes-agent <cmd>` 绕过脚本** —— 脚本补了 `HOME`/`PATH`，裸 sudo 缺环境变量，行为不对
2. **别在 hermes-agent 里再 sudo** —— 见上，那条报错就是这么来的
3. **别为了预览去改 sudoers** —— 不需要。`preview` 零特权：`ui/` 有 ACL 可读，`index.html` / `js/fusion-v030.js` / `scripts/marked.min.js` 三个 URL 实测全 200

### 三种预览方式（按需要选）

| 想干什么 | 命令 | 需要什么 |
|---|---|---|
| 看配色/布局，反复刷新 | `dev/hermes-dev.sh preview 8917` → `http://127.0.0.1:8917/` | 零特权，vector 直接跑 |
| 带真数据截图验收 | `dev/hermes-dev.sh probe --shot-dir /tmp/after` | 脚本内部提权，不用管 |
| 看真实交互 | 浏览器开真面板 `http://<nas-ip>:8650/` | 无（后端一直在跑） |

`preview` 是纯静态的：**消息气泡、工具区块、表格不会渲染**（没数据），只能看骨架和配色。
要验证气泡/表格请用 `probe`（连真机）或直接开真面板。

## 4. 备份与回滚

### 4.1 三个时点各做什么

| 时点 | 动作 | 命令 |
|---|---|---|
| 改之前 | 让 git 记住现状 | `git commit -am "pre: ..."`（UI/JS 在 SRC_REPO；Python 在 PY_SRC 自动可 diff） |
| 部署时 | 自动留 .bak | `deploy` 内置，落 `$HERMES_HOME/backups/<文件>.<时间戳>.bak` |
| 大改前 / 升级前 | 整机快照 | `dev/hermes-dev.sh snapshot` → `$HERMES_HOME/backup/snapshots/hermes-<ts>.tar.gz`（约 56M，含关键 4 文件 + 两个仓库 bundle） |

快照里有什么：`ui/index.html`、`server/monitor.js`、`cmd/main`、`config.yaml`、`hermes-src.bundle`、`fpk-src.bundle`。异地放一份到 `/vol1/1000/飞牛文件/` 或你自己的机器。

### 4.2 回滚

```bash
# UI / monitor.js
dev/hermes-dev.sh rollback ui/index.html
dev/hermes-dev.sh rollback server/monitor.js
dev/hermes-dev.sh restart

# Python
cd /vol1/@appcenter/hermes-agent/hermes-src
git checkout -- agent/xxx.py        # 单文件
git stash / git reset --hard 715201b   # 整体回到基线（危险，会丢所有未提交改动）

# 从快照还原整个 Python 层
cd /tmp && tar xzf $HERMES_HOME/backup/snapshots/hermes-<ts>.tar.gz ./hermes-src.bundle
git clone /tmp/hermes-src.bundle restored && rsync -a --exclude .git restored/ /vol1/@appcenter/hermes-agent/hermes-src/
```

### 4.3 升级后要做的事

升级会**整目录覆盖** `$APP_DIR`（含 `hermes-src`）。升级完立刻：

```bash
dev/hermes-dev.sh repair      # 1) 重建 Python 层的 .git 指针与排除表
dev/hermes-dev.sh status      # 2) 看运行文件 vs git 源是否又不一致了
git -C $SRC_REPO log --oneline -5   # 3) 确认 UI/JS 的补丁提交还在

# 4) 认领被升级冲掉的 Python 补丁（repair 只重建指针，不恢复代码）
cd /vol1/@appcenter/hermes-agent/hermes-src
git status --porcelain | head -20   # 被覆盖后与 HEAD 的差异 = 我们的补丁被冲掉的痕迹
git diff --stat HEAD                # 差多少行，哪些文件
git checkout HEAD -- agent/xxx.py   # 单个文件：把我们那版盖回来
# 若官方这个文件也更新过 → 先 git diff HEAD -- agent/xxx.py 看两边，手工合并，别整个盖
```

## 5. 雷区（每条都真踩过）

1. **`cp` 覆盖运行文件会改属主** → fnOS 写 PID 失败 → 无限重启。用 `cat src > dst`（`deploy` 已封）。
2. **重启只有一条命令**（见 2.4）。`monitor-api restart` 不重启 monitor 主进程。
3. **升级整目录覆盖 `$APP_DIR`**：UI/JS 改完必须回流 `SRC_REPO` 并 push；Python 靠 git + 快照。
4. **diff 运行文件 vs git 源会看到上万行假差异**（运行文件 CRLF，源 LF）：
   `diff <(tr -d '\r' < 运行) <(tr -d '\r' < 源) | wc -l` → 0 才是真一致。
5. **改 `fusion-v030.js` 必须 bump `?v=` 版本号**，否则缓存假象。
6. **别起第二个 gateway**（共享 state 会被写坏）。
7. **`/compress` 是物理删除旧消息**，不是折叠，别当 bug 修。
8. **monitor.js 每 180s 自愈重写 config.yaml 的 mcp_servers 块**：改这块先 `grep -c _unquoteMcpVal server/monitor.js`（应 ≥4），确认递归反转义补丁还在。
9. **控制面板会话有两套存储**：面板 `$TRIM_PKGVAR/chat/sessions/<uuid>.json`；agent `$HERMES_HOME/state.db`。改标题要分清。
10. **`read_file`/`search_files` 读 `/var/apps/...` 不稳定**（sandbox overlay），grep 不到不等于没有，用 python 直读。
11. **node 和 venv python 的二进制是 `-rwxr-x---`**，vector 直接执行会 Permission denied；`hermes-dev.sh` 内部自动绕 `sudo -u hermes-agent`。
12. **`cmd/main` 别动**，PID 属主坑的源头。
13. **git 报 `dubious ownership`** 时（vector 改 hermes-agent 属主的仓库必然遇到，本机已替它配好）：
    `git config --global --add safe.directory <仓库路径>`
14. **重启会掐断正在跑的会话**：`restart` / `deploy server` 是**全应用**重启（gateway + dashboard 一起死），正在执行的对话会中断，未落盘的会话可能丢。动手前先看 `status` 有没有长任务在跑；有人在用面板时先说一声。
15. **`config.yaml` 别手改**：Hermes 内核运行时会把部分字段回写覆盖，monitor.js 每 180s 还会重写 `mcp_servers` 块。走面板接口或 `hermes config set`，改完用 `status` 核对。

## 6. 改完怎么交差

1. `git commit`（两个仓库各自提交，message 写清改了什么、为什么）
2. `git push`（SRC_REPO 有 Gitea remote；PY_SRC 是本机仓库，需要异地就靠 snapshot）
3. 写一条改动记录，放 `$HERMES_HOME/knowledge/项目/YYYY-MM-DD-<主题>.md`：
   - 动了哪些文件、为什么
   - 验证手段与结果（probe 截图路径 / 日志片段 / md5）
   - 已知副作用、未验证的部分
   - 怎么回滚

内部 agent 下次开会话靠这条记录知道自己被谁改了什么。**不写这条，等于埋雷。**

## 7. 出事了怎么办

| 症状 | 先查 | 处置 |
|---|---|---|
| 面板打不开 | `dev/hermes-dev.sh status`、`tail -50 $LOGDIR/info.log` | `rollback ui/index.html` → `restart` |
| 面板能开但功能全挂 | 浏览器 console（`probe --eval`）、`hermes.log` | 同上，回滚 monitor.js |
| agent 不回话 | `gateway.log` 末尾、`hermes doctor` | `git checkout` 改动 → `restart` |
| 应用反复重启 | `ls -l /vol1/@appdata/hermes-agent/app.pid` 属主 | 必须 `hermes-agent`；是 root/vector 就 `sudo chown hermes-agent: /vol1/@appdata/hermes-agent/app.pid` |
| 端口冲突 | `ss -lntp \| grep -E '8650\|8742\|9219'` | 杀掉冲突进程后 `restart` |
| 升级后功能丢失 | `dev/hermes-dev.sh status` 的 md5 对比 | 从 SRC_REPO 重新 `deploy`，或从快照还原 |
