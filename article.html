这台 NAS 上的 Hermes，被我改成了什么

1424 次提交、658 KB 单文件拆到 71 KB、面板能在 macOS 上跑起来。改了什么、突破了什么、跟上游是什么关系。

先分清三个名字，不然后面全是糊涂账

「Hermes」这个词在这套系统里指三样不同的东西，混着说就会得出「你重写了 Hermes」这种荒谬结论。

是什么 谁做的 我动了吗
Hermes 模型 一组开源大模型权重（Hermes 3 / Hermes 4 系列） Nous Research 没动。 它只是可选的模型后端之一，本机现在跑的是 DeepSeek，也能切到别的
Hermes Agent Agent 运行时本体，hermes-agent 0.20.0，pip 包 Nous Research 基本没动内核。 这是地基，我的活不在这一层
fnos-hermes-panel 运行在本机上的网页控制面板 + 打包 + 跨平台启动器 我做的 改动全在这一层

一句话：Nous 给了引擎，我把车改装成了一台能开出门的车。

下面说的所有事，都发生在第三层。

起点：一个 658 KB 的 HTML

Hermes Agent 装到 fnOS 上之后，自带一个网页控制面板，用来管对话、会话树、模型切换、技能、MCP、定时任务、记忆、用量、终端、通讯渠道、隧道。

它的初始形态是一个 658 KB 的 index.html：

134 KB  内联 <style>
470 KB  内联 <script>
557 个函数，全挤在同一个作用域里

不是因为代码写得丑，而是因为它每天咬人三下：

问题 实际表现
单文件即单点 任何一个字符打错，整个面板白屏。没有「局部失败」这回事
谁后加载谁赢 同名函数在 3 个地方定义，改对 2 处，第 3 处静默覆盖，改了等于没改
部署是 cp 拷过去就算发布。拷一半、拷错目录、源和目标不同步，全靠人眼发现

第二条最贵。真实例子：提示函数 toast 有新旧两版，新版在 ui-kit.js，老版在 utils.js。老版在文件里位置更靠后，所以老版一直赢——组件层建好了但没生效，视觉退回硬编码样式，而且没有任何一处报错。

这类问题的共同点是：代码能跑、现象正确、改动静默失效。 靠 review 和测试都抓不住，因为不报错。

所以拆的目标从一开始就不是「让文件变短」，是让「改哪一处会生效」变成可以查的。

改了什么：把结构手术搬到正在使用的生产系统上

一个不允许妥协的约束

面板跑在用户（也就是我）的 NAS 上，天天在用。所以整个重构的验收标准不是「看起来差不多」，而是不允许有行为变化：

  • 全局函数 638 个、全局对象 314 个，拆前拆后集合零差异
  • 1440×1000 与 390×844 两种视口截图，禁动画后逐像素 0 差异
  • 生产目录与源码目录 SHA-256 逐文件对账

这个约束逼出了全部验证工具。没有它，这个项目会在第二次提交时失控。

结果

index.html   658 KB → 71 KB   (-89%)
剩下的 71 KB  没有一行业务逻辑，只有静态骨架 + 资源清单 + 76 个 <script> 标签
app/ui        8.2 MB         40 个 JS 模块
app/server    7.6 MB         前后端体量对等 —— 不是只改了皮肤

分层是四层，加载顺序即依赖顺序：

js/core/     12 个   地基：utils / ui-kit / api / state / router / theme / markdown
js/chat/      6 个   对话：会话树 / 气泡 / 流式 / 输入 / 斜杠命令 / 语音 / 圆桌
js/panels/   12 个   面板：概览 / 模型 / 定时 / 扩展 / 记忆 / 用量 / 渠道 / 隧道 / 终端
js/panel-*.js 36 个  历史遗留：功能都在用，职责与 panels/ 重叠

那 36 个遗留文件如实写在文档里，不假装不存在。它们要真正归入三层，得动 36 个正在使用的文件，收益低于风险——这条债我认。

1424 次提交的分布

app/ui          1358     前端，主战场
dev/tests        874     测试，几乎等于前端
app/server       538     后端
config/prompts   155     提示词

测试量和前端改动量几乎相等，这个数字比任何形容词都能说明这套东西是怎么长出来的。

突破性进展：四件以前做不到的事

一、从「改完不知道生不生效」到三层等价验证

这是整件事的核心。三层验收，一层比一层狠：

层面 做法 拦得住什么
符号级 全局函数/对象集合逐个比对，638 / 314 零差异 漏搬、重复定义、静默覆盖
样式级 计算样式逐项对比 类名对但规则没生效、优先级被压
像素级 两种视口截图，禁动画后逐像素 diff 上面两层都对但看着不一样

第二层曾经抓到过「假绿」：截图 diff 是 0，但顺手打开 Network 一看，两个页面都是坏的——错误页长得一样，所以 diff 也一致。

从此这条写进了流程：diff 为 0 不等于对，得先确认两边都在正常工作。

二、从「靠人记」到机器门禁

规矩写进文档没人看。所以做成了 arch_lint：分层违规、循环依赖、未归类文件，一律报出来拦下去。

有意思的是它的第一步：先允许 103 条违规通过，然后一条条消。如果一上来就全拦截，第一天就干不下去。

三、从「只能跑在飞牛上」到跨平台

面板原来紧绑 fnOS 的 Unix socket。改了三处 monitor.js 加一个 113 行的启动器 bin/hermes-panel.mjs，让它能退化到纯 TCP。

macOS arm64 实测（macOS 27.2.1 / node v18.20.8，不设 MONITOR_SOCKET_PATH）：

UI_PORT=8650     → HTTP 200 / 72,962 B
28 秒内自愈 0 次、端口冲突 0 次
--port 8660      → 同样跑通

这意味着一台 Mac、一台 Windows、一台 NAS 上跑的是同一套面板代码。

四、从「拷文件发布」到账本 + 对账

部署不再是 cp：走账本、可回滚、发布后拿源码目录和生产目录逐文件比 SHA-256。改了什么、上没上、上得对不对，三个问题都有答案。

与上游的差异

「上游」在这里有两层，分开说。

相对 Hermes 模型：没有关系

模型只负责推理。换模型不涉及本项目任何一行代码——本机现在跑 DeepSeek，昨天可能跑别的，面板不用改。

相对 Hermes Agent：同一台引擎，不同的车

Hermes Agent 原版 这套改造
面板形态 自带一份 Web UI 同一份 UI，拆除 4 层 40 模块，658 KB → 71 KB
运行平台 主要跑在 Linux / fnOS 加启动器与降级路径，macOS 实测通过
发布方式 从包里取 打包成 .fpk，应用中心一键装，两套 CLI 双活，OAuth 自动续期
验证手段 靠人看一眼 符号 / 样式 / 像素三层等价 + 架构门禁 + 生产 SHA-256 对账
架构约束 无强制 arch_lint 机器拦截，文档说了不算，脚本说了算
知识沉淀 无 三百多条技能 + 三层知识库，全在本机，不进任何云
数据位置 依部署方式 全部落本机：会话、记忆、技能、凭据都在自己盘上

没有做的事也要说清楚：Agent 内核的推理循环、工具调度、模型接入层，我基本没碰。这套改造补的是产品化、可运行性、验证纪律、本地数据层，不是「让 Agent 更聪明」。

新功能：面板上多出来的那些东西

不是造了新模型，是把 Agent 的能力变成了能点、能看、能管的东西。

对话与协作

  • 会话树：按项目分组的会话列表、分支 Fork、引用、语音条
  • 多 Agent 圆桌：一个人不够就叫专家开会，多个角色并行讨论后汇总
  • 专家库 315 位（面板口径；人格库源文件 268 条）：不同专业角色卡片，可单独启停
  • 中途插话：Agent 正在跑的时候能打断、补充、改方向
  • 审批闸门：危险操作先问再做，不是事后告诉你做完了

能力管理

  • 技能库 361 个：随手装、随手关，一个不开也不挡路
  • MCP 接入：外部工具服务器配置、启停、健康检查
  • 能力开关：Task Planning 这类模块单独关，不用整包卸载
  • 模型管理：多家供应商、限流自动切下一家、凭据隔离、本地端点

运维

  • 定时任务：可视化编辑器、执行历史、钩子
  • 用量与成本：按会话归因，看清钱花在哪
  • 终端 / 工作区 / 文件
  • 通讯渠道：QQ、微信、飞书、Discord、Telegram 各渠道配对
  • 隧道与远程访问

稳定性

  • 配置自愈：配置坏了能自己恢复
  • 压缩与上下文治理：长会话自动压缩，控制 token 账
  • 维护面板：健康巡检、磁盘、进程

真实使用量（2026-11-15 实测）

会话    597 条（累计，消息 37.2 万条）
        其中 api_server 303 / cron 165 / discord 59 / 微信 18 / QQ 12 / 飞书 6
技能    361 个（SKILL.md 实际落盘数）
专家    315 位（面板口径，后端 data.total）
        Agency 人格库实际落盘 268 条，市场专家 15 条，内置 16 条

口径不一的地方我照实写：面板显示的 315 和人格库文件的 268 不是同一个统计口径，前者可能合并了多个来源。没核准的地方不硬凑成一个数。

没做完的部分，写在明面上

已经做到 还差什么
面板能在 macOS 跑通 Windows 只做了启动器适配，没真机长跑过
36 个遗留文件功能都在用 没真正归入三层，动了风险大于收益
架构门禁能拦违规 规则是人写的，人想绕就能绕
部署有账本可对账 升级还得手动下包覆盖，没有自动更新
本地数据全在自己盘上 备份要自己做，没有托管方案
技能 361 个能用 没有市场，换台机器不会自动同步

回头看

做对的：

  1. 先定「不允许有行为变化」，再动手 —— 这个约束逼出了全部验证工具
  2. 每切一块都验符号 —— 638 这个数字每次切完都查，比任何 code review 有效
  3. 把规矩写成可执行检查 —— 文档没人看，arch_lint 会拦
  4. 诚实记录债 —— 36 个未归类文件、38 处 confirm() 都写在文档里，不假装没有

靠运气的：

  1. 拆分顺序 —— 切错会陷进循环依赖，我是试出来的，不是设计出来的
  2. 假绿那次的发现 —— 如果当时没顺手看一眼 Network，这个项目会带着一个假的验收结论收工

最大的收获不是这套代码，是那句反复验证的话：

代码能跑、现象正确、改动却静默失效 —— 这类问题只能靠「量化」抓，不能靠「看」。
